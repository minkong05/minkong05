### ▎Project Case Studies

**LDR Platform — Mini SOC Platform** · *solo · v1.0.0, feature-complete · built over 16 weeks*
![FastAPI](https://img.shields.io/badge/FastAPI-009688?style=flat-square&logo=fastapi&logoColor=white) ![Flask](https://img.shields.io/badge/Flask-000000?style=flat-square&logo=flask&logoColor=white) ![PostgreSQL](https://img.shields.io/badge/PostgreSQL-4169E1?style=flat-square&logo=postgresql&logoColor=white) ![Docker](https://img.shields.io/badge/Docker-2496ED?style=flat-square&logo=docker&logoColor=white) ![MITRE ATT&CK](https://img.shields.io/badge/MITRE_ATT%26CK-C0102D?style=flat-square)

**The Challenge:** Turn raw Flask/Nginx logs into something an analyst can actually act on — not a log viewer, but real detection, investigation, and response with a defensible audit trail.

**The Solution:** Three Python services. An ingest API normalises logs into an ECS-inspired schema; a polling worker evaluates 6 YAML threshold rules over sliding windows, each mapped to a MITRE ATT&CK technique, and writes alerts; a Flask dashboard — a pure API client with no database connection of its own — lets an analyst triage, pivot to an IP's timeline, and block/unblock, with every action chained into a tamper-evident SHA-256 audit log.

```
Agent → Ingest API → Normaliser → Event Store (Postgres)
                                        ↓
                                Detection Worker (YAML rules)
                                        ↓
                                 Alert Writer → Email
                                        ↓
                             Investigation Dashboard
                                        ↓
                           Response Actions → Audit Log
```

**Worth a look:**
- An **attack simulation CLI** that fires synthetic attacks per rule, checks which rules actually fired, and regenerates a detection-coverage report — including an explicit statement of what the suite does *not* cover. Refuses to run in a production environment.
- **LLM alert summarisation, defended against prompt injection** — off by default; every attacker-controlled log field is HTML-escaped into delimited tags behind a system-prompt boundary, and the client never raises, so a failed summariser can't break the alert page. Threat model written up in `docs/ai-security-notes.md`. Designed after a session on how the trust hierarchy between system, developer and user input collapses once everything shares one context window.
- Layered auth — ingest token, separate backend API token, session login with analyst/admin RBAC, CSRF on every state-changing form.
- Unit tests on SQLite plus integration tests against real PostgreSQL, in CI alongside lint, format check and migrations, with ruff pinned identically across venv, pre-commit and CI.

**Verafield — EUDR Regulatory Compliance Platform** *(team project · backend feature-complete)*
![FastAPI](https://img.shields.io/badge/FastAPI-009688?style=flat-square&logo=fastapi&logoColor=white) ![Pydantic](https://img.shields.io/badge/Pydantic-E92063?style=flat-square&logo=pydantic&logoColor=white) ![PostgreSQL](https://img.shields.io/badge/PostgreSQL-4169E1?style=flat-square&logo=postgresql&logoColor=white) ![Alembic](https://img.shields.io/badge/Alembic-2C2D72?style=flat-square) ![Docker](https://img.shields.io/badge/Docker-2496ED?style=flat-square&logo=docker&logoColor=white) ![Argon2id](https://img.shields.io/badge/Argon2id-4B275F?style=flat-square)

**The Challenge:** Independent oil-palm smallholders in Sabah and Sarawak need to prove EU Deforestation Regulation compliance — resolving what documents they hold against a versioned state-tenure rulebook, cross-checking field signals for anomalies, and assembling it all into an evidence pack a mill can send to its EU buyer.

**The Solution:** A FastAPI backend across thirteen routers, all eleven MVP features taken from schema through migration to endpoint. Multi-tenant isolation is enforced in the schema, not by convention — every tenant table carries a `UNIQUE(id, mill_id)` constraint and every child row's foreign key is composite on `(parent_id, mill_id)`, so one tenant's records can't be linked to another's even if application code forgets to filter. A versioned rules engine resolves state + land type to exact required documents, a verification engine routes inconsistent field signals to human review, and an evidence-pack generator assembles cleared records into a regulator-mapped output only once every flag on the batch clears.

```
Mill Dashboard (teammate)     Field Collector (teammate)
              ↘                     ↙
        auth + tenant-scope dependency
      Argon2id · minimal-claim bearer token
                          ↓
           backend/routes — 13 routers (mine)
                          ↓
                   Rules Engine
     state + land type → required docs (versioned rulebook)
                          ↓
                Verification Engine
      deforestation test + Five-Point Field Check
                          ↓
        inconsistent ──→ needs_review queue (human)
                          ↓ cleared
              Evidence Pack Generator
        Annex II JSON + GeoJSON  →  mill  →  EU buyer
```

**Worth a look:**
- **Auth built into a codebase that previously had none.** Argon2id hashing, and a bearer token carrying only subject, issued-at and expiry — role and tenant are deliberately *not* in the token but re-read from the database on every request, so deactivating an account takes effect immediately rather than at token expiry. Authorisation runs as a route dependency that reconciles the tenant named in the URL with the tenant proved by the credential, before any route body executes.
- **No account-enumeration oracle.** A wrong password, an unknown email and a deactivated account return identical responses, and a lookup miss still runs an Argon2 verification against a fixed dummy hash so response time can't leak whether an account exists.
- **Built to survive an audit.** RESTRICT rather than CASCADE on both foreign keys into the tenant registry, so deleting an operator can never cascade away a five-year regulatory trail — and every assessment stores the exact rule row it was resolved against, so a decision made years earlier stays reproducible against the rulebook as it stood at the time.

*Team project. This card covers only the FastAPI backend, the shared `packages/shared_types` contract, and the Python tooling — my own work. The React/TypeScript mill dashboard and the offline field-collector app are built by a teammate; both integrate against my API through the shared-types contract, without touching the service or database layers directly. (The repo is named Verafield; the codebase is branded TAPAK internally.)*

**Flask-LearnPython — Security-Focused Learning Platform** · *solo*
![Flask](https://img.shields.io/badge/Flask-000000?style=flat-square&logo=flask&logoColor=white) ![CSRF](https://img.shields.io/badge/CSRF_protection-212C42?style=flat-square) ![Rate Limiting](https://img.shields.io/badge/Rate_limiting-212C42?style=flat-square) ![Docker Sandbox](https://img.shields.io/badge/Docker_sandbox-2496ED?style=flat-square&logo=docker&logoColor=white)

**The Challenge:** An interactive Python-learning platform needs to let users run their own code — a textbook remote-code-execution risk if done carelessly.

**The Solution:** User code never touches the Flask process. It's forwarded, authenticated via a shared secret, to a separate sandbox service that runs it in a throwaway Docker container with no network access and hard resource limits — backed by login gates, rate limits, and a code-length cap on the Flask side.

```
Browser
   ↓
Flask App   (login required · rate limit · 1000-char cap · timeout)
   ↓  X-SANDBOX-SECRET
Sandbox Service   (separate process, :5001)
   ↓
Docker container   (--network=none --memory=128m --cpus=0.5 --pids-limit=32)
```

**Worth a look:**
- The repo states explicitly that **keyword and blacklist filtering is not the security boundary** — container isolation is. Filtering is defence in depth, not the control.
- Tier-based authorisation resolved per request rather than trusted from the session, and CSRF applied globally with explicit, commented exemptions for webhook and JSON endpoints rather than silent ones.
- PayPal IPN webhooks verified by posting the payload back to PayPal instead of trusting the inbound request.
- Threat model, route-by-route attack surface, sandbox rationale and a bug ledger all documented; CI runs the suite credential-free.
